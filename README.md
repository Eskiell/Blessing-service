# Blessing - cheats

Blessing is a standalone PS5 payload with a Vue 3 interface for listing and
toggling cheats for the currently running game. Vite builds the frontend as a
single `dist/index.html`, which is embedded directly into `blessing.elf` and
served locally by the payload.

The OnionHEN engine migration is documented in
[`docs/ONIONHEN_MIGRATION_PLAN.md`](docs/ONIONHEN_MIGRATION_PLAN.md).
For an architectural overview and the complete cheat-toggle flow, see
[`docs/CODE_ARCHITECTURE.md`](docs/CODE_ARCHITECTURE.md). Adapted code and
fixtures are identified in [`THIRD_PARTY_NOTICES.md`](THIRD_PARTY_NOTICES.md).

## Development

```sh
cd frontend
npm install
npm run dev
```

## Build

```sh
git clone https://github.com/Eskiell/ez-cheats.git
cd ez-cheats
export PS5_PAYLOAD_SDK=/path/to/ps5-payload-sdk
make all
```

The build produces `blessing.elf` using C++20 and embeds the HTML generated by
Vite. The currently used SDK does not include libc++, so the codebase uses C++
classes and RAII over the SDK's libc without depending on the C++ standard
library. This boundary can be revisited if libc++ is added to the toolchain.

Run the host test suite with:

```sh
make host-test
```

Send the ELF to the console with:

```sh
make deploy PS5_HOST=ps5-ip-address
```

Build settings can be overridden from the command line:

```sh
make all HTTP_PORT=5911 \
  CHEATS_DIRECTORY=/data/ez-cheats/cheats \
  MEMORY_BACKEND=automatic
```

`MEMORY_BACKEND` accepts `automatic`, `mdbg`, or `kdirect`. Automatic mode
detects the console firmware. See the [operations guide](docs/OPERATIONS.md)
for installation, security, and troubleshooting details, and complete the
[PS5 test checklist](docs/PS5_TEST_CHECKLIST.md) before publishing a release.

## Cheat files

The runtime searches the flat directory `/data/ez-cheats/cheats`. Each filename
must follow `<TITLE_ID>_<VERSION>.<format>`, for example
`PPSA00001_01.002.003.json`.

When more than one format exists for the same game and version, precedence is:

1. `.json`
2. `.shn`
3. `.mc4`
4. `.ShnExt`

Title IDs and versions are validated before paths are constructed. The
repository rejects symbolic links and tracks path, inode, size, `mtime`, and
`ctime` to reload files automatically after they are replaced or edited.
Nested distribution trees are not processed by the payload; a separate
installation tool must flatten them when necessary.

## Game platform

The PS5 adapter queries the running BigApp, associates its App ID with system
processes, and provides the PID, Title ID, name, version, platform, and process
name. Metadata is read from PS5 `param.json` or PS4 `param.sfo` files. The
adapter can also locate loaded modules by name and retrieve their memory
sections. When no game is running, the query succeeds without a game context
(`pid` and `appId` are both `-1`).

SDK-specific headers and calls remain in
`src/platform/ps5_game_platform.cpp`; the domain, service, and host tests do not
include SDK dependencies.

## Memory backends

The engine provides `mdbg` and `kdirect` memory backends. In automatic mode,
firmware versions earlier than 8.40 use mdbg, while firmware 8.40 and later use
kdirect. Callers can also force either backend. Every write can be confirmed by
an immediate readback through `write_verified`.

Code-cave mapping aligns the range to 16 KiB pages, attaches to the process
with RAII, executes a fixed-address `mmap`, applies RWX protection, and always
restores registers and detaches—even on error paths. Kernel, mdbg, and ptrace
APIs remain isolated in `src/memory/ps5_memory_backends.cpp`.

## Applying cheats

`CheatApplier::set_enabled` resolves the module in the main process or another
process with the same App ID, calculates absolute or relative addresses, and
confirms every write through readback. PS2 patches use absolute addresses.
Master codes are detected and used to adjust dependent patches when required.

Before each mutation, the current bytes are saved. If any patch fails, all
previously processed patches are restored in reverse order; the `enabled` state
changes only after the complete operation succeeds. A PID change invalidates
all previous states. A code cave is attempted only while enabling an unreadable
address whose restore bytes have the same length.

The payload exposes:

- `GET /`
- `GET /health`
- `GET /api/v1/version`
- `GET /api/v1/cheats`
- `PUT /api/v1/cheats/:id`

The cheat endpoints use the real service. The payload detects the game through
the PS5 adapter, loads `/data/ez-cheats/cheats`, selects the memory backend, and
verifies writes before reporting a cheat as enabled.

## Backend contract

### `GET /api/v1/cheats`

```json
{
  "connected": true,
  "backend": "mdbg",
  "error": null,
  "game": {
    "titleId": "CUSA00001",
    "name": "Running game",
    "version": "1.00",
    "platform": "ps4"
  },
  "cheats": [
    {
      "id": 0,
      "name": "Infinite health",
      "description": "Keeps health at its maximum value",
      "author": "Author",
      "enabled": false
    }
  ]
}
```

### `PUT /api/v1/cheats/:id`

Request body:

```json
{ "enabled": true }
```

The response returns at least `id` and `enabled`, reflecting the state actually
applied by the cheat engine.

Errors use `{"error":"code","message":"details"}`. A toggle without a
running game returns `409`; an unknown ID returns `404`; module or memory
failures return `422`; and internal service unavailability returns `503`. All
state responses use `Cache-Control: no-store`.

Mutations accept only the embedded frontend origin and require the
`X-EZ-Cheats-Request: 1` header. This prevents a page from another origin from
changing game memory through the user's browser.
